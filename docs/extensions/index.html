Create your own Extension

Everything installable in FocusCaseX is described by one catalog entry plus a folder of small files — no build tools, no bundler. This page is the full authoring guide; the full guide carries the same walkthrough in its Extensions section.

A text editor and the fcx command are enough: build, test on your own machine, then submit to the marketplace — or zip the folder and ship it as one file.

The five kinds

Pick the kind that matches what you are building — the kind decides which files the installer fetches and where they land:

  • Extension — a tool that adds a feature: commands, panels, automations. Two files: manifest.json + main.js. (The first kind in every example below.)
  • Capsule — a ready-made board or page section. A spec.mdui layout file, plus optional style.css and logic.mdui.
  • Theme — the workspace look. One JSON file of design tokens.
  • Template — a pre-written clinical note or letter. One markdown file.
  • Snippet — a small interface tweak. One CSS file.

A WorkBench is the sixth entry kind — a bundle that installs many items at once. It is assembled from published items, so build an Extension or two first if you want to ship one.

What an installed item looks like

The CLI installer fetches exactly the files the catalog entry lists and writes them into a folder named after the item, one folder per kind. An Extension always lands as manifest.json and main.js (plus any extra files the entry lists); a capsule keeps its spec.mdui, style.css and logic.mdui; a theme its JSON; a template its markdown; a snippet its CSS. Every install is registered in the CLI's installed list, which is what fcx install list and fcx uninstall read.

How the catalog describes an item

A real entry from the marketplace catalog — the Heading Numbering Extension — so you can see the exact shape:

{ "id": "plugin:heading-numbering", "kind": "plugin", "name": "Heading Numbering", "tagline": "Auto-numbers H2/H3 headings in the reading view using an injected CSS counter (cleaned up on unload).", "description": "Auto-numbers H2/H3 headings in the reading view using an injected CSS counter (cleaned up on unload).", "author": "FocusCaseX originals", "version": "1.0.0", "category": "Writing", "tags": ["plugin", "writing"], "icon": "ListTree", "rating": 4.1, "reviews": 64, "downloads": 4207, "released": "2026-01-24", "verified": true, "featured": false, "meta": { "pluginId": "heading-numbering" }, "files": { "manifest": "plugins/heading-numbering/manifest.json", "main": "plugins/heading-numbering/main.js" } }

The rules that matter:

  • id is kind:slug — plugin:hello-clinic-note, capsule:ui-today, theme:mono-ink. The slug is the folder name under plugins/, capsules/, themes/, templates/ or snippets/ in the site repo.
  • files points at those paths — for an Extension the keys are manifest and main; a capsule lists spec (plus style, logic); a theme lists vars; a template lists body; a snippet has a top-level file.
  • meta carries the bare id — pluginId, capsuleId, themeId, templateId — matching the manifest's own id.
  • rating, reviews, downloads, released, verified and featured are marketplace metadata — the review fills those in; you can leave them out of a new entry.

The minimal Extension — a worked example

"Hello clinic note" — one command and one small stylesheet, in the same shape as the shipped samples. Two files, nothing else.

File 1 of 2 — plugins/hello-clinic-note/manifest.json
{ "id": "hello-clinic-note", "name": "Hello clinic note", "version": "1.0.0", "minAppVersion": "1.0.0", "description": "A first Extension — one command on the palette and a starter style for clinic notes.", "author": "Your name" }
File 2 of 2 — plugins/hello-clinic-note/main.js
/** * FocusCaseX Extension — Hello clinic note. * One command, one injected stylesheet, cleanup on unload — the same * shape as the shipped samples (registerCss, registerCommand, showToast). */ (function (ctx) { "use strict"; var css = [ ".clinic-note-starter {", " border: 1px solid var(--line);", " border-radius: 10px;", " padding: 14px 16px;", " color: var(--ink-2);", "}" ].join("\n"); ctx.registerCss(css); ctx.registerCommand({ id: "hello-clinic-note", title: "Hello, clinic note", icon: "FileText", run: function () { ctx.showToast("Hello clinic note is installed and running."); }, }); ctx.onunload = function () { /* the injected stylesheet leaves with the host cleanup */ }; })(ctx);
The catalog entry that publishes it
{ "id": "plugin:hello-clinic-note", "kind": "plugin", "name": "Hello clinic note", "tagline": "A first Extension — one command on the palette and a starter style for clinic notes.", "description": "A first Extension — one command on the palette and a starter style for clinic notes.", "author": "Your name", "version": "1.0.0", "category": "Writing", "tags": ["plugin", "writing"], "icon": "FileText", "meta": { "pluginId": "hello-clinic-note" }, "files": { "manifest": "plugins/hello-clinic-note/manifest.json", "main": "plugins/hello-clinic-note/main.js" } }

For the other kinds the same two-part pattern holds — a folder of files plus an entry that lists them. A theme entry's files.vars points at a JSON of design tokens; a template's files.body points at a markdown note with frontmatter (patient: MR-0000 and a type); a snippet lives in the catalog's top-level snippets array as { "id", "name", "file", "description" } pointing at one CSS file.

Test it locally

The CLI reads its marketplace from a URL, so you can point it at your own machine while you build. Make a mirror folder that looks like the site:

mirror/ catalog.json ← a copy of the catalog with your entry added to "items" plugins/ hello-clinic-note/ manifest.json main.js

Serve the folder with any static file server, then point the CLI at it and sync:

FCX_MARKET_URL=http://localhost:4319 fcx sync FCX_MARKET_URL=http://localhost:4319 fcx install plugin:hello-clinic-note

fcx sync fetches catalog.json from that URL and caches it; fcx install resolves the item by id, install code or name and writes its files into the workspace — the output shows the folder and the install code. Every install prints the same shape; here it is for the Heading Numbering item quoted above, installed from the marketplace:

fcx install plugin:heading-numbering
OK manifest.json OK main.js ╭─────────────────────────────────────────────────────────────────╮ │ Installed Heading Numbering v1.0.0 │ │ Code FCX-NX338Z │ │ Where …/workspace/extensions/heading-numbering │ ╰─────────────────────────────────────────────────────────────────╯ Enable it in the app: Settings → Extensions → install by code FCX-NX338Z

The install lands in the CLI's installed list — the list fcx install list prints and fcx uninstall edits:

fcx install list
╭────────────────────────────────────────────────────────────────────────────────────────────────────╮ │ Name Kind Version Code Directory │ │ Heading Numbering extension 1.0.0 FCX-NX338Z …/workspace/extensions/headin… │ │ Midnight Plus theme 1.0.0 FCX-XKPJSD …/workspace/themes/midnight-p… │ ╰────────────────────────────────────────────────────────────────────────────────────────────────────╯ 2 items installed fcx uninstall <id-or-code> removes one.

Install by code works too: every item's FCX-XXXXXX code is derived from its id, so once your entry is in a catalog, its code exists and resolves the same everywhere — the site, the app and the CLI.

Share the mirror with the clinic. fcx serve hosts the synced cache for everyone: it prints a local URL, and a LAN address when a clinic network exists. No clinic network? The web workspace still opens as usual.

Submit it

  1. Add your entry to catalog.json in the public site repo (stromplayz/FocusCaseX) — in items, or in the top-level snippets array for a snippet.
  2. Add the files the entry points at, at exactly those paths: plugins/<slug>/, capsules/<slug>/, themes/<slug>.json, templates/<slug>.md or snippets/<slug>.css.
  3. Open a pull request — or hand the entry and files to the FocusCaseX owner, and the review takes it from there. Review fills in the marketplace metadata and marks reviewed items.

After it merges, one fcx sync picks the item up on every machine, the marketplace pages list it with its install code, and installs by code work in the app and the CLI alike. Shipping an update: bump version in the catalog entry and your manifest — the next install overwrites the old files.

Ship it as one file

The marketplace is one way to publish; the same folder can also skip it entirely. Zip it, rename the zip to .fcxext, and the file itself is the installer — a pack. Send it by email, hand it over on a USB stick or drop it in a shared clinic folder, and whoever receives it runs one command. Nothing is fetched from a catalog and no network is needed — no marketplace round trip.

hello-clinic-note/ manifest.json ← id, kind, name, version main.js zip the folder → hello-clinic-note.zip → rename it → hello-clinic-note.fcxext

One file does the naming: manifest.json sits at the top of the archive — the same manifest the folder already carries, with the .fcxext extension on the file telling the installer the kind. If the zip was made with right-click → compress, everything usually lands in one wrapper folder, like hello-clinic-note/manifest.json; when every file shares that single wrapper, the installer strips it automatically and the pack installs flat. Both store and deflate compression read fine, so any zip tool works. Pack support is built into fcx install in FocusCaseX 3.1.0.

Installing is the one command: fcx install hello-clinic-note.fcxext installs straight from the file itself. The files land in the workspace folder for their kind, next to anything installed from the marketplace; the install shows up in fcx install list like any other, and fcx uninstall removes it the same way. Every other kind travels the same recipe — .fcxtheme, .fcxcapsule, .fcxwb, .fcxtemplate, .fcxsnippet — and the full pack-format specification, every manifest field included, lives at one-file packs in the full guide, with the install shown as a demo under the CLI's own pack section.

Two copies, one code. The command prints an FCX-XXXXXX install code for the pack — enter it in the app under Settings → Extensions → install by code and the identical item is enabled there. The pack and the marketplace install of the same id are the same item, so the printed code matches the one on the marketplace page too.
