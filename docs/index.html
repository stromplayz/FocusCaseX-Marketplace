The short version

What is FocusCaseX

FocusCaseX is an offline-first clinic workspace for eye care. It runs on your device — a phone, a tablet, a computer — and your records live there with it. There is no server to rent and nothing to host: install it, sign in once, and the clinic is open. A day in it looks like this: you register a patient and the chart file creates itself, you run the refraction and exam flows, manage optics, dispensing and billing, and set recalls — while the boards for appointments, recalls, billing and stock read the same files and show the day at a glance. Pages stay readable and printable no matter what.

Three ideas carry the design:

  1. Pages are markdown. Every clinical page is a plain text file you can read, print and keep. No opaque database, no lock-in.
  2. Capsules are building blocks. A short block pasted into any page renders a live board — appointments, vitals, recalls.
  3. Extensions are features. Small add-ons from the marketplace — an extra panel, an automation, a quick reference — installed in one tap, removed just as easily.

The ecosystem at a glance

Everything installable comes from one catalog, and the marketplace is where you browse it — in the app, on this site, or in the terminal. Eight names cover the whole map:

  • Extensions — one-feature add-ons from the marketplace: an extra panel, an automation, a quick reference, installed and removed in one tap. Build your own: the Extensions guide.
  • Capsules — ready-made boards you drop into any page as a short pasted block: appointments, vitals, recalls. The capsule guide.
  • Themes — one JSON file of design tokens that re-skins every surface of the workspace at once. Themes.
  • Templates — pre-written clinical notes and letters, one markdown file each, ready to fill in. Browse them in the marketplace.
  • Snippet — a small interface tweak in one CSS file, like bigger headings. Also in the marketplace.
  • WorkBenches — a whole clinic setup packed into one install: Extensions, capsules, a theme, templates and starter pages, applied in a single step and switched like modes. WorkBenches.
  • FCX CLI — the same catalog and licence flow from a terminal, through the fcx command. Installing the CLI.
  • Android app — FocusCaseX on phones and tablets; it checks for updates on its own and tells you inside the app when one is ready. The Android app.

Three ways to open the clinic

Same workspace, same licence, three doors:

  1. The web workspace. focuscasex.vercel.app opens in any browser, anywhere — nothing to install, and it is always the current build.
  2. The Android app. Carries the clinic on phones and tablets, fully offline — records live on the device, and the day's work needs no connection. The Android app.
  3. A computer with the CLI. The fcx command brings the marketplace, the WorkBenches and the licence flow to any computer that runs Node 18 — macOS, Linux or Windows (WSL/Git Bash). Set up the CLI.

Sharing with the front desk. Sharing a clinic over a local network happens only when the clinic network exists; with no clinic network, the web app still opens as usual — everyone signs in at focuscasex.vercel.app from wherever they are.

One licence under all of it

FocusCaseX is licensed per clinic, and the licence travels as a code: FCX-XXXXXX, issued by your clinic owner and bound to one email. A device activates once with that code and is remembered as a trusted device from then on — it never asks again. Every code carries a device limit, two devices by default; when a machine is retired or replaced, the clinic owner frees the slot by revoking it, or raises the limit. The flow is the same at both ends: the apps ask once at first launch, and on a computer fcx login asks for the licence email, the password and the code issued for that machine. What the licence check sends, what never leaves the device, and how revoking works: security and privacy, and signing in from the CLI.

That is the whole picture. Everything else on this page — the CLI, the marketplace, authoring, WorkBenches, security, troubleshooting and the glossary — hangs off those three ideas and that one licence. For clinics, non-technical

Start in seven steps

Seven steps from an empty room to a working clinic day — and not one of them needs a technical person. The workspace speaks plain English on the equipment you already have, and your licence details are the only paperwork involved.

What to have ready

Your licence email and password, and the FCX-XXXXXX activation code from your licence email. That is the whole list. Whichever way you open FocusCaseX, the same clinic waits inside — the same catalog and the same install codes — so the ways mix freely: the web on the front-desk computer, the app on the testing-room tablet, the CLI wherever a keyboard is quicker.

  1. Open FocusCaseX. Three ways in, and every one opens the same clinic. The web workspace opens in any browser at focuscasex.vercel.app — nothing to install first. Phones and tablets use the Android app instead: the install guide links the latest APK — download it to the device, allow the install when Android asks, and open FocusCaseX from your app list. Computers can also install the FCX CLI, covered under Install the CLI.
  2. Sign in. Enter your licence email and password — the account your licence runs on. Tick Keep me signed in and the next visit skips the sign-in form.
  3. Activate the device, once. A device the licence has not met yet asks for the FCX-XXXXXX code from your licence email. Type it once — the device is remembered from then on. It becomes a trusted device under your licence, and trusted devices never ask again.
  4. Register your first patient. Open the Patients board and tap register. The patient file creates itself, and the MR number creates itself with it — there is no numbering scheme to invent and nothing to set up first.
  5. Run the day from the boards. Appointments, examination, dispensing and billing are boards in the sidebar. Record vision, fill in the workup, write the plan — everything lands in the patient's chart file. The tour of the workspace walks each board in order.
  6. Add what your clinic needs. Open Settings → Marketplace and browse. Extensions add features, capsules add ready-made boards, themes change the look, templates drop in pre-written notes — every install is one tap, and you see exactly what will be added before it lands. More under The Marketplace. Packs can also arrive as files: load one straight from the file, and the confirmation screen lists every piece before anything is applied — see Packs.
  7. Let it update itself. The app checks for updates on its own and tells you when one is ready — nothing to revisit, no store page. The web workspace is always current, so a browser refresh is all it takes.

Sharing with the front desk. When your clinic has its own network, the workspace can be shared across it — the guide's clinic-network section shows how, with the fcx open command opening the same clinic for every computer on that network. No clinic network? Nothing changes: the web app still opens as usual, and everyone signs in from wherever they are.

Deeper detail lives on the Getting started page — the requirements, the activation screen in full, and uninstalling. Plain-language questions — where records live, what happens offline, who sees what — have short answers in the troubleshooting section of this guide.

The full ecosystem, A to Z

The workspace, board by board

One Tuesday, open to close: the front desk opens the Today board at half past eight — four booked refractions, one walk-in already waiting, two recalls due. The walk-in registers in a minute and gets an MR number; the first patient's chart pre-fills the examination workup; by noon two spectacle orders are at the lab and a claim has gone out; in the afternoon the Recall board names everyone overdue and a recall letter prints; at close, the Day Sheet sums the day. Every step of that day touches a board in the same workspace. This section walks all of them, A to Z.

  • Today board. The day at a glance: appointments, walk-ins and recalls due, with the day's totals on top. The Today's patients capsule reads the book as triage chips and patient rows, so the front desk and the chair see the same queue.
  • Patients. Register a patient once — the file and MR number follow them across every visit. The Patient header capsule resolves identity and recall status from the file, Visit history lists every stored visit newest first, and the Patient directory board adds one-tap register, book and call with live counts of patients seen today and recalls overdue.
  • Examination flow. The Examination workup capsule runs the full clinical flow with both eyes side by side — history and vitals, objective and subjective refraction, motility and binocular vision, adnexa, tear film, anterior segment, IOP and gonioscopy, posterior segment and special tests, out to a plan with medications, procedures and a fee. Beside it sit the Visual fields board for reliability and MD/PSD progression, the IOP watch board for target-versus-current pressure, and the CL fitting log for contact-lens trials, parameters and next review. The Essential Diagrams Extension adds labeled anterior-segment and fundus diagrams for OD and OS straight into the exam note — see Extensions.
  • Notes. Every clinical page is a plain markdown file — readable, printable, yours. Drop in a template and the page becomes a usable note: Refraction note, Glaucoma workup, Visual field follow-up, Cataract pre-op sheet, Contact lens fitting and CL aftercare & progress are all in the marketplace.
  • Rx pad and letters. The Spectacle Rx pad template prints a clean prescription from the exam values, and the Referral letter and Medical necessity letter templates draft the paperwork a surgeon or an insurer expects. The Referral Composer Extension prefills the referral from the active chart, and Quick Phrases expands chairside shorthand with patient variables.
  • Appointments and recalls. The Appointment board is the front-desk day book: booking and rescheduling, walk-ins, no-shows, payment chips and day, week and month views — slots never lock. The Recall board computes overdue follow-ups from visit advice, and the Recall Campaigns Extension turns an overdue list into a finished outreach campaign, with the Recall letter template ready to print.
  • Dispensing and orders. Frames, lenses and lab jobs move through the Lab job board from promised date to pickup, and the Purchase orders board follows every supplier order from draft to paid. The Dispensing & order template keeps the spectacle order with the patient's chart.
  • Inventory and stock alerts. The Inventory board covers lenses and frames with reorder flags, and the Stock Alerter Extension flags the moment stock dips below reorder — before a busy Saturday finds an empty tray.
  • Billing and claims. The Billing desk is the front desk's to-bill, dispensing and unbilled worklist; the Claims board follows insurance from eligibility and pre-auth through denials and pending rupees; and the Day Sheet Extension prints an end-of-day summary in one tap.
  • Cohorts and reports. Diagnosis cohorts build chronic-care registers from keyword rules; the Clinic overview board puts business KPIs over any range next to the clinical-load row; Trend charts draw a field's progress across visits as a sparkline, and Stat tiles post the headline numbers.
  • Communications. The Comms log keeps every call, SMS and WhatsApp to or from a patient beside their chart, so who was told what never depends on memory.
  • Documents and files. Scanned slips, field prints and prescriptions land in the Scan index as tappable cards, and each patient file keeps its documents beside the visits they belong to.
  • Settings. Themes, snippets, Extensions and the licence all sit in one place: choose a theme, add the Chairside VA snippet so VA and Rx numerals read at arm's length from the chair, turn Extensions on or off, and check when the licence renews.

Boards you can add

Capsules are ready-made boards you drop into any page — paste a two-line block and a live board renders, reading your own records. The catalog carries 28 of them, from the Today's patients and Examination workup boards down to single patient blocks like the Vitals panel and Visit history. What a capsule is and how to place one is covered under capsules, and the full set is browsable in the capsule marketplace.

Extensions add whole features rather than single boards: Optomize runs the optometry EMR suite and stores follow-up visits as compact deltas, so only the values that changed since the last visit are written; Recall Campaigns, Stock Alerter, Day Sheet, Referral Composer and Quick Phrases each own one job. Installing and managing them is covered under Extensions, and the catalog lives in the Extensions marketplace.

A WorkBench configures the whole setup at once — one install of a complete EMR. The Solo Optometrist WorkBench applies 10 Extensions, 28 capsules, 13 templates, 7 snippets and the Solo Optometry theme to a fresh clinic in a single step; how it works is under WorkBenches.

The same clinic on every screen. Everything reads and prints the same on phone, tablet and computer, and when the workspace is shared over LAN the whole team sees the same boards. The look changes with a theme — Paper Light for the desk, Clinical Ice or Surgical for the chairside screen — picked up under themes, and not a single record moves when it does.

For computers

Install the FCX CLI

The FCX CLI is the clinic workspace from the terminal: the same marketplace, the same WorkBenches and the same licence flow as the app, on any computer that runs Node 18 or newer — macOS, Linux, or Windows through WSL or Git Bash. The current build is 3.1.0, and one command puts it on your machine.

One command, then a fresh terminal

Open a terminal — Terminal on macOS or Linux, WSL or Git Bash on Windows — and paste the line below. It fetches the installer from the FocusCaseX registry and runs it. There is nothing else to click and no package manager to learn.

curl -fsSL https://stromplayz.github.io/FocusCaseX/install.sh | bash

When the installer finishes, open a fresh terminal window — a new one, not the same tab — so the newly installed fcx command is picked up, then check which build you are on:

fcx version
focuscasex 3.1.0

That one line is the whole verification. If the fresh window says fcx cannot be found, the old terminal is still holding the pre-install PATH — close it, open another, and run the check again.

What the installer does

In plain words, three things. It checks that Node 18 or newer is on the machine and tells you clearly if Node needs attention first. It puts the fcx command in place. And it wires your PATH — bash and zsh — so typing fcx works in any new terminal window. Nothing else changes: patient records, app settings and installed Extensions are not part of this install — on a computer none of that exists yet, and the setup wizard below creates it.

The CLI is open about how it is built: the source code and the release history live in public on GitHub, in the stromplayz/FCX-NPM repository.

A fresh install announces itself in one line when you ask for help:

fcx help

One command, four steps

The setup wizard

Once the CLI is installed, one command gets a computer ready for its first clinic day: fcx setup. The wizard walks through four short steps, asks every question in plain English, and finishes with a summary checklist so you can see at a glance what was chosen. Arrow keys move between the choices and enter picks one. Two of the steps can be skipped, so the run can be as full or as light as the day allows. The commands that come after it — signing in, browsing, installing — have their own sections on the CLI page.

The four steps

  1. Workspace folder. The wizard asks where installed items should live on this machine and checks that the folder is writable before moving on. Accept the suggested folder or name your own — the --dir option answers this step in advance.
  2. Catalog. The marketplace catalog is synced into a local cache, so browsing and installs keep working even when the clinic network is slow. Keeping that cache healthy is covered at fcx vitals and care.
  3. Sign in. Enter the licence email, the password and the FCX-XXXXXX activation code for this device. Skippable — signing in on its own is described at fcx login and the device licence.
  4. First WorkBench. Pick a WorkBench bundle and the wizard installs it, so the machine ends the run with a working clinic setup instead of an empty workspace. The bundles are listed at WorkBench bundles.

Run it

Type the command and follow the prompts, or copy it from here:

fcx setup
fcx setup

fcx setup --yes --skip-login --skip-workbench

Sign in, check, move on

Account and licence

Five commands look after the licence on a clinic machine: sign in, check where you stand, print the device card, see who is signed in, and sign out. All five speak plain English and finish in seconds. The licence itself stays in the clinic's hands: the owner issues the codes, sees every device on the admin Devices page, and revokes a machine the day it retires.

Sign in with fcx login

fcx login signs the machine in to the clinic licence. It asks three things, in order — and on a machine that has signed in before it asks for none of them, because a trusted device re-verifies quietly on its own. Through a pipe the same questions come back as plain prompts, so a script can sign a machine in too.

Three prompts, once per machine

  1. The licence email. The email the clinic licence runs on.
  2. The password. Typed with masking, so it never shows on screen.
  3. The FCX-XXXXXX code. Issued by the clinic owner for this machine — one code per device. When the code passes, the machine becomes a trusted device under the licence and counts against the code's device limit.

That is the whole ceremony — once per machine. Trusted machines never re-enter a code: run fcx login again and it re-verifies quietly, with no prompts. The guided setup wizard signs in the same way, so a first install can pass through it on the way (see First-run setup). And if the older word suits you, fcx activate does exactly the same thing — it is the same command under its former name.

Where you stand: fcx status

fcx status prints the device's licence card — the licence email, this device's id and the moment it was activated — and re-checks it against the licence registry in the same run, the verdict carried on the card itself. On a machine that has not signed in yet, it says so plainly:

fcx status
Not activated — run fcx login.
# a fresh machine, before its first sign-in

The re-check matters when a device leaves the clinic: if the owner has revoked this machine, fcx status says so and exits with code 1, so a scheduled script and a quick glance both catch it. Network trouble is a warning, not a crash — the licence card stays where it is. fcx status --json prints the stored licence record and the registry's verdict as JSON, ready for that script to parse.

One line of identity: fcx whoami

fcx whoami answers with a single line naming the signed-in email and the device id — or, on an unactivated machine, a pointer back to fcx login:

fcx whoami
Not signed in — run fcx login.
# the same fresh machine

On a signed-in machine the line reads signed in as <email> · device <id> · cli — printed on the spot, with no registry round trip and exit code 0 either way, so a shell script can use it as a guard.

The device card: fcx device

fcx device prints the full identity card for this machine — its label, the system it runs, CPU and memory, storage, and the runtime underneath the CLI. It is the same view the clinic owner has on the admin Devices page, and it carries no secrets: it describes the hardware, never the licence. Add --json and the same identity card comes back as one JSON payload.

Signing out: fcx logout

fcx logout removes the device licence from the machine. On a terminal it asks you to confirm first, and if the keepalive check-in is running it stops that too, so the machine stops checking in with the registry. Signing out is a local step only — it does not free the licence slot. The slot is freed on the admin Devices page, where the owner revokes the device: the same page that issued this machine's code. On a machine with no licence to remove, fcx logout says so and changes nothing.

Browse, install, remove

Marketplace and catalog

The marketplace is one catalog with two front doors: the browser at the marketplace site and, on any computer with the fcx command (set up first under Install the CLI), the terminal. Every item — Extensions, capsules, themes, templates, snippets and WorkBench bundles — carries its own FCX-XXXXXX install code, and the same code works in both places. This section covers the terminal side: browsing the storefront, installing by code, checking what the machine carries and removing what the clinic no longer needs.

The storefront in the terminal — fcx marketplace

fcx marketplace — alias fcx market — opens the full-screen storefront in the terminal: items grouped under their categories, / to search by name, and an item page for every entry with its description, rating and install code. Press i on a list row and the item installs on the spot; the item page installs with i or enter; esc steps back one level and q quits. On a terminal, bare fcx install opens the same storefront — browsing and installing are one motion. The storefront needs a real terminal: driven through a pipe it exits at once with a hint to use fcx catalog instead, so it never sits waiting for keys that never come.

Install one item — fcx install <id-or-code>

fcx install <id-or-code> installs one item. It accepts an exact item id, an FCX-XXXXXX code, or any piece of an item's name, matched case-insensitively. When a name piece fits several items, the CLI lists the candidates and stops — nothing is guessed — so the exact code is the way to be certain. Remove an item — fcx uninstall <id-or-code>

fcx uninstall <id-or-code> takes an item back off the machine. It resolves the argument the same way install does — exact id, FCX-XXXXXX code or name piece — deletes the item's folder from the workspace, and updates the installed list. On a terminal it asks before it removes; piped input removes immediately, which is what a cleanup script wants. A normal morning

The whole loop, five moves from a fresh sync to a tidy workspace:

  1. Sync — fcx sync refreshes the cached catalog, so browsing and installs see every current item.
  2. Browse — fcx marketplace opens the storefront; search with / and read the item page before you install.
  3. Install — press i in the storefront, or run fcx install FCX-NX338Z to go straight to one item.
  4. Enable it in the app — Settings → Extensions → install by code, using the same FCX-XXXXXX code the install printed.
  5. Remove what is not needed — fcx uninstall <id-or-code> when a trial Extension did not earn its place.

A pack is a zip, renamed

One-file packs, straight from the file

Every installable item in FocusCaseX is a folder of small files. Zip the folder, rename the zip to the item's pack extension, and the file itself becomes the installer: send it by email, copy it on a USB stick or drop it in a shared clinic folder, and whoever receives it runs one command — no marketplace round trip. Pack support is built into fcx install in FocusCaseX 3.1.0, and the command reads the pack straight off the file itself; nothing is fetched from a catalog and no network is needed.

The six pack extensions

Each kind travels in its own pack file — the extension on the file says what the zip holds:

What must be inside

One file does the naming: a manifest.json at the top of the pack, carrying the item's id, kind (extension, theme, capsule, template, snippet or workbench), name and version. A WorkBench pack is the one exception — the bundle's workbench.json takes its place, because the bundle already describes everything it installs. And if the zip was made with right-click → compress, everything usually sits in one wrapper folder, like My Extension/manifest.json; when every file shares that single wrapper, the installer strips it automatically and the pack installs flat. Two shortcuts keep a manifest tiny: leave the id out and the pack's file name supplies it; leave the kind out and the pack's extension decides. Any ordinary zip works — the entries may be stored (uncompressed) or deflated, which is what every common archiver writes — and anything else is refused with a re-pack hint.

Whole setups, one install

WorkBench commands

A WorkBench is a whole clinic setup packed into one install — boards, ready pages, a theme, templates, snippets and starter settings travelling together as a single bundle. On a computer with the fcx command (see Install the CLI), three subcommands cover everything: fcx workbench list, fcx workbench show and fcx workbench install. Each one prints what it found or did in plain columns and checklists, so you see the whole setup before anything lands.

What a WorkBench is

One install, one clinic. A WorkBench gathers the Extensions, capsules, theme, templates, snippets and starter pages a working practice needs, plus starter settings for the editor and appearance. Instead of installing pieces one at a time, you install the bundle and the workspace is configured in a single step. The published bundle for one-chair practices is the Solo Optometrist WorkBench — browse it at the WorkBench marketplace page, and the walkthrough for building and saving your own is at WorkBenches.

  2. fcx alive — the keepalive daemon

The keepalive daemon re-checks this machine's licence with the registry on a schedule — any interval from 5 to 1440 minutes, 10 by default, and a value outside the range is pulled back inside it — so the admin Devices page always shows this machine as current. The licence itself stays private on the machine; security and privacy explains what activation checks and what it never shares.

A simple care routine

There is no schedule to memorise — this is the whole routine, and most machines need it once:

  1. Check the machine. After setup — or any time something looks off — run fcx vitals and read its eight lines. Basics OK plus warnings pointing at what has not been done yet is a healthy machine.
  2. Sign in and start the keepalive. Run fcx alive start once per machine after signing in — see the account section. From then on the licence re-checks itself on its schedule and the Devices page stays current without anyone remembering to.
  3. Refresh the catalog. Run fcx sync after setup and whenever the marketplace adds something new, so the catalog list stays fresh.
  4. Check for a newer build. Run fcx update now and then. If it prints an install command, copy that line, run it, done.
  5. Look back when curious. Glance at fcx stats to see what a machine has been doing, and leave fcx config until you actually want to change a setting.

Let an assistant read the clinic

MCP is a standard way for AI assistants — Claude, Cursor, VS Code and more — to talk to a tool. Every add-on belongs to one of six kinds. The kind decides what the installer fetches and where the item lands in your workspace:

Installing

Browsing works the same everywhere: browse by category, open an item for its description, rating and install code, then install in one tap.

Themes

One switch changes every surface — the boards, the editor, printed output — while every record stays exactly where it is. A theme remaps fonts, colors and shapes across the whole workspace in a single tap, and it goes back to the native FocusCaseX look just as fast.

What a theme is

A theme is one JSON file of design tokens — the palette, the type, the corner shapes, the accent colors. Because it is tokens and not logic, it changes how the workspace looks without changing how it works: patients, charts, notes and every other record keep their place.

Every theme listed below is on the marketplace and installs with one tap, like everything else on the shelf. Switching does not reinstall anything and moves no data — the look simply swaps.

Ready-made boards for any page

Capsules

A capsule is a ready-made board or page section you drop into any page. Paste its short block and the page renders a live board — appointments, vitals, recalls, stock — drawn from the records your clinic already keeps.

What a capsule is

Capsules are building blocks. A short block pasted into any page renders a live board, and the board moves with the data behind it: the appointment board writes straight back into the day book, and the recall board computes overdue follow-ups from visit advice. Nothing on screen is a picture of the board — it is the board your staff tap.

They come in two families. Boards whose ids start with ui- cover the working day, from the front desk to the lab. Sections whose ids start with emr- resolve a single patient file, so a patient header or a trend chart can sit inside a clinical page.

Using a capsule

  1. Open Settings → Marketplace and browse the Boards and Patient categories. From a terminal, fcx install takes any catalog item — Extensions, capsules, themes, templates — by exact id, FCX code or a name substring.
  2. Confirm with the entry in view: every install shows exactly what will be added before it lands, and the CLI fetches exactly the files the catalog entry lists.
  3. Paste the capsule's short block into any page, or add the board where your staff already work.
  4. The page renders the live board — today's patients, claims, lab jobs — and stays current with the records behind it.

The three files inside

A capsule is built from up to three files. spec.mdui is the layout — the fields the board shows and how they sit. style.css is its look. logic.mdui is optional behavior; in the current catalog only the appointment, patients and examination capsules ship one.

A real example — the Vitals panel capsule's spec.mdui is two lines:

patient: MR-1042
show: va, iop, rx

Point the block at a patient, choose the fields, and the board resolves VA, IOP and Rx chips for the patient's latest visit.

Authoring

Create your own Extension

Everything installable in FocusCaseX is described by one catalog entry plus a folder of small files. No build tools, no bundler — a text editor and the fcx command are enough, and this is the complete, hands-on guide: the five item kinds, the catalog entry behind every listing, a working Extension built end to end in ten minutes, the local test, and the pull request that publishes it. The same text lives on the Extensions authoring page.

The five kinds — and a sixth

Pick the kind that matches what you are building — the kind decides which files the installer fetches, which pack extension the item travels in, and where it lands after install:

  • Extension — a tool that adds a feature: commands, panels, automations. Two files: manifest.json + main.js. (The first kind in every example below.)
  • Capsule — a ready-made board or page section. A spec.mdui layout file, plus optional style.css and logic.mdui.
  • Theme — the workspace look. One JSON file of design tokens.
  • Template — a pre-written clinical note or letter. One markdown file.
  • Snippet — a small interface tweak. One CSS file.

A WorkBench is the sixth entry kind — a bundle that installs many items at once: Extensions, capsules, a theme, templates, snippets, starter pages and a settings snapshot. It is assembled from published items, so build an Extension or two first if you want to ship one; a WorkBench installs through its own flow and lands as one bundle folder with every piece inside. The full picture is under WorkBenches.

What an installed item looks like

The CLI installer fetches exactly the files the catalog entry lists and writes them into a folder named after the item, one folder per kind. An Extension always lands as manifest.json and main.js (plus any extra files the entry lists); a capsule keeps its spec.mdui, style.css and logic.mdui; a theme its JSON; a template its markdown; a snippet its CSS. Every install is registered in the CLI's installed list, which is what fcx install list and fcx uninstall read — the commands are covered under marketplace and catalog. The installer's summary names the folder it created, and the app switches the item on once it is installed there too, by the same install code.

How the catalog describes an item

Every listing on the marketplace is one JSON entry in the site's catalog.json. Here is a real one — the Heading Numbering Extension — exactly as it appears, so you can see the shape your own entry joins:

{
  "id": "plugin:heading-numbering",
  "kind": "plugin",
  "name": "Heading Numbering",
  "tagline": "Auto-numbers H2/H3 headings in the reading view using an injected CSS counter (cleaned up on unload).",
  "description": "Auto-numbers H2/H3 headings in the reading view using an injected CSS counter (cleaned up on unload).",
  "author": "FocusCaseX originals",
  "version": "1.0.0",
  "category": "Writing",
  "tags": ["plugin", "writing"],
  "icon": "ListTree",
  "rating": 4.1,
  "reviews": 64,
  "downloads": 4207,
  "released": "2026-01-24",
  "verified": true,
  "featured": false,
  "meta": { "pluginId": "heading-numbering" },
  "files": {
    "manifest": "plugins/heading-numbering/manifest.json",
    "main": "plugins/heading-numbering/main.js"
  }
}

The rules that matter:

  • id is kind:slug — plugin:hello-clinic-note, capsule:ui-today, theme:mono-ink. The slug is the folder name under plugins/, capsules/, themes/, templates/ or snippets/ in the site repo.
  • files points at those paths — for an Extension the keys are manifest and main; a capsule lists spec (plus style, logic); a theme lists vars; a template lists body; a snippet has a top-level file.
  • meta carries the bare id — pluginId, capsuleId, themeId, templateId — matching the manifest's own id.
  • rating, reviews, downloads, released, verified and featured are marketplace metadata — the review fills those in; you can leave them out of a new entry.

Build one in ten minutes

A working Extension, start to finish: my-first — one command on the command palette and one small stylesheet, in the same shape as the shipped samples. Five steps:

  1. Make a folder — my-first/, with exactly two files in it: manifest.json and main.js.
  2. Write main.js — the Extension API shape every shipped sample follows. Both files are fenced below.
  3. Test locally with the CLI — fcx install takes a pack file or an item id: zip the folder into a .fcxext pack and install it straight off the file (one-file packs), or point the CLI at a local mirror of the catalog, as below.
  4. Add a catalog entry — the JSON that publishes the item; fenced below.
  5. Send a pull request to the marketplace — the exact steps are under Publish it, below.
Step 1 — my-first/manifest.json
{
  "id": "my-first",
  "name": "My first Extension",
  "version": "1.0.0",
  "minAppVersion": "1.0.0",
  "description": "A first Extension — one command on the palette and a starter style for clinic notes.",
  "author": "Your name"
}

Five fields is the whole manifest: what it is called, what it does, who made it, and the app build it expects. Note the id is the bare slug — my-first — and the catalog entry's meta repeats it, which is what keeps the two files in step.

Step 2 — my-first/main.js
/**
 * FocusCaseX Extension — my-first.
 * One command, one injected stylesheet, cleanup on unload — the same
 * shape as the shipped samples (registerCss, registerCommand, showToast).
 */
(function (ctx) {
  "use strict";

  var css = [
    ".my-first-note {",
    "  border: 1px solid var(--line);",
    "  border-radius: 10px;",
    "  padding: 14px 16px;",
    "  color: var(--ink-2);",
    "}"
  ].join("\n");

  ctx.registerCss(css);

  ctx.registerCommand({
    id: "my-first",
    title: "Hello, clinic note",
    icon: "FileText",
    run: function () {
      ctx.showToast("my-first is installed and running.");
    },
  });

  ctx.onunload = function () {
    /* the injected stylesheet leaves with the host cleanup */
  };
})(ctx);

The shape to copy: ctx.registerCss injects a stylesheet; ctx.registerCommand puts one command on the palette — it takes an id, a title, an icon and a run function; ctx.showToast raises a toast; ctx.onunload is the cleanup hook that runs when the Extension leaves. The shipped samples all follow it, so any of them is a second example to read.

A whole clinic setup, one install

WorkBenches

A WorkBench is a whole clinic workspace packed into one install: Extensions, capsules, a theme, templates, snippets, starter pages and starter settings. Installing one reshapes the workspace in a single step — the boards, the pages, the look and the note formats all land together after one confirmation — and switching between installed WorkBenches works like switching modes. Wherever the workspace goes, your records never move.

What a WorkBench is

Where a single Extension adds one tool, a WorkBench changes the shape of the whole workspace in one step: which boards greet the day, which pages exist, how the app looks, how notes and letters start. The app lists every piece before you confirm, then shows progress as each one lands. Every WorkBench you install becomes a mode — one tap in the app's WorkBenches tab switches the whole workspace to that setup, and one tap switches it back. Modes are setups, not storage: switch as often as the day requires, and nothing is ever deleted along the way.

What one install can carry:

  • Extensions — the tools and automation, from an EMR engine to recall campaigns and stock alerters, each landing under Settings → Extensions. Author your own with the Extensions guide.
  • Capsules — the live boards the starter pages call into: appointment book, recalls, claims, lab jobs. Capsules.
  • Theme — the workspace look, applied on install and reverted just as easily. Themes.
  • Templates — pre-written notes, letters and forms that install as real files, ready to copy into a patient chart.
  • Snippets — small interface tweaks, switched on by the settings snapshot.
  • Starter pages — ready dashboard pages with their full content embedded in the bundle, so a fresh workspace opens to a working day.
  • Settings snapshot — editor, appearance, quick actions and per-Extension switches, applied with everything else.

Assemble your own

Any clinic or developer can build one. The rule that keeps it simple: a WorkBench assembles items that are already published, so the pieces go first and the bundle points at them.

  1. Publish the pieces first. Put each Extension, capsule, theme, template and snippet on its own into the catalog — authoring starts at the Extensions guide, publishing at the marketplace.
  2. Assemble the bundle JSON. One workbench.json: id, name, description, version, then a contents block listing every item by id and version, group by group, exactly as the skeleton above shows.
  3. Add starter pages with content embedded. Each entry carries a path, a title and the whole page inside the bundle, so a new clinic opens to working dashboards. On install, missing pages are created and an existing page always wins — a clinic's edits survive every re-apply.
  4. Choose a theme and a settings snapshot. The theme object and the settings block ship in the same bundle and apply with the rest, so the workspace behaves as designed from the first launch.
  5. Ship it two ways. Publish the bundle as a catalog item, or wrap it as a .fcxwb one-file pack and hand the file to a colleague or a second branch — see Packs and installing packs. The full walkthrough is at the WorkBenches page.

Setup only — the boundary. Applying a WorkBench never touches patient records and never deletes anything: it adds tools, pages and settings, and your case files stay exactly where they are. Removing happens per item afterwards — under Settings in the app, or with fcx uninstall on a computer. Curated bundles live in the marketplace's WorkBenches section.

Pack formats, A to Z

The official one-file pack specification, and the principle fits in one line: a pack is a normal ZIP of the item's folder, renamed — the file itself is the installer, on any computer with the CLI, and loads straight from the file in the app. Zip the folder, swap the extension, send it by email, USB or a shared clinic folder, and the receiver installs it with one command — no marketplace round trip, nothing fetched. Pack reading is built into FocusCaseX 3.1.0 and parses the ZIP format itself, so packaging needs nothing more than any standard zip tool.

The six formats

Each kind travels in its own file extension. Zip the item's folder, rename the archive, and the file extension tells the installer — and the app — what is inside:

Extension What it is Inside Rename-to
.fcxextAn Extensionmanifest.json + main.jsmy-extension.zip → my-extension.fcxext
.fcxthemeA ThemeThe theme's JSON filemy-theme.zip → my-theme.fcxtheme
.fcxcapsuleA Capsulespec.mdui + style.css + logic.mduimy-capsule.zip → my-capsule.fcxcapsule
.fcxwbA WorkBench bundleworkbench.json + any loose files it referencesmy-setup.zip → my-setup.fcxwb
.fcxtemplateA TemplateThe template's markdownletter.zip → letter.fcxtemplate
.fcxsnippetA SnippetThe snippet's CSStweak.zip → tweak.fcxsnippet

clinic-vitals/
  manifest.json   ← id, kind, name, version
  main.js         ← the code

The manifest

One file names the item. At the top of the pack sits a manifest.json, a small JSON object carrying the item's id, kind, name and version, plus an optional description — a tagline field is read in its place when description is absent:

{
  "id": "plugin:clinic-vitals",
  "kind": "extension",
  "name": "Clinic Vitals",
  "version": "1.2.0",
  "description": "Adds a vitals trend panel to the patient board."
}
Field What it holds
idThe item's id. If it already carries its kind prefix — plugin:clinic-vitals above — the installer keeps it exactly as written; without a prefix, the right one is added from the kind. Omitted, it falls back to the pack's file name without the extension.
kindOne of extension, theme, capsule, template, snippet or workbench. A manifest writes "extension" for an Extension pack; it is stored as FocusCaseX's internal plugin kind and displayed as Extension everywhere a person can see it. Omit it and the pack file's own extension supplies the kind.
nameThe display name shown in listings and in install output. It falls back to the pack's file name when omitted.
versionThe item's version, shown after install and kept with the installed entry. Optional, but worth setting.
descriptionAn optional one-line description read from the manifest. A tagline field is read in its place when description is absent; with neither, it is simply left empty.

A WorkBench pack is the one exception: instead of manifest.json it carries the bundle's workbench.json, and that bundle takes the manifest's place — it already names the setup and lists everything it installs. Loose files riding along in a .fcxwb land under files/ next to the bundle, so it keeps working offline.

Zip and rename

From folder to installer in five steps:

  1. Build the item's folder as its authoring guide describes — Extensions, Themes, Capsules and WorkBenches each list the exact files.
  2. Zip the folder with any standard zip tool — store (uncompressed) and deflate both work.
  3. Rename the .zip to the pack extension for its kind — one of the six in the table above.
  4. Send it anywhere: email, a USB stick or a shared clinic folder. The file is the whole installer.
  5. The receiver installs it: fcx install clinic-vitals.fcxext on a computer, or open/load it straight from the file in the app — Android included (see the Android guide).

Rules the installer enforces

A pack cannot install halfway and cannot write outside its folder. The checks are built into the CLI:

Rule What it means
Manifest at the top — requiredmanifest.json (or, for a WorkBench pack, workbench.json) must sit at the top level of the zip; without it the pack is refused, with a message saying exactly that.
One wrapper folder is strippedZips made with right-click → compress usually wrap everything in a single folder; when every entry shares that one root, the installer removes it so the pack installs flat.
Paths cannot escape the install folderEvery entry's path is checked before it is written, so a crafted ../ name cannot land outside the item's own folder.
Store and deflate both workUncompressed and deflated entries are both read; any other compression is refused with a re-pack hint.
Encrypted or zip64 archives are not supportedThe zips in this guide never need them — re-pack with a standard tool, no encryption.

Packs keep the marketplace honest. The same folder can be published to the marketplace and shipped as a pack — nothing is forked or reformatted between the two, so what a clinic receives as a file is what the listing serves. After a pack install the CLI prints an install code; enter it in the app under Settings → Marketplace → install by code and the identical item is enabled there. The command's own page is at one-file packs, and the marketplace command covers the other half.

Where your records and your licence stand

Security and privacy

Two plain promises hold the workspace together: your patient records stay on your device, and the licence stays in the clinic's hands. This page spells out both — what stays local, what the licence allows, and exactly what crosses the network and when.

Your records stay on your device

Patient data lives in the workspace on your device. Day-to-day work — registering patients, running exams, writing notes, managing recalls — needs no connection at all, and nothing is sent anywhere during daily work. First activation on a new device is the one moment that needs a connection: the code is checked once, and after that the device is trusted and the clinic runs offline. Export anything, any time — patients, notes and recalls come out as plain files you keep, so your data is never locked inside the app.

The licence belongs to the clinic

FocusCaseX is licensed per clinic, and the licence travels as a code: FCX-XXXXXX, bound to one email. The licence carries a device limit — two devices by default. Activation happens once per device: sign in with the licence email, enter the code, and the device is added. A trusted device is remembered and never asks for a code again — same device, no prompts.

The clinic owner manages all of this on the admin Devices page: every device the licence runs on is listed there, so the owner always sees which machines run FocusCaseX. A lost or retired machine is revoked to free its slot, and fresh codes can be issued at any time. Password resets happen on the licence, by the owner — nothing on the device changes, and the records stay exactly where they are.

Moving a licence to a new device

The approval cannot be handed over: it lives on the device, private to you — never printed, never synced, and there is no file you can copy to move it. A new machine earns trust the same way the first one did, by activating. That takes three steps, all in the open.

  1. Free the slot — the clinic owner revokes the lost or retired device on the admin Devices page.
  2. Activate the new device — sign in with the licence email and enter the FCX-XXXXXX code. While the licence is under its device limit, the existing code works; the owner can issue a fresh one if that is easier to hand over.
  3. The old device stops — it asks for a code at its next launch and cannot pass without one the owner issues. Revoking touches the licence check only: the records on that machine are right where they were.

What travels over the network

Two moments touch the network, and neither involves patient records. Activation and the periodic licence check send hardware identity only — device model, OS version, screen metrics, app build, locale and a per-device identifier. That is the complete list: it is what tells devices apart, and it is shown back to the licence owner, so a code never lands on an anonymous machine. Patient records never leave the device during activation, and the periodic licence check sends the same kind of identity, nothing more.

Extensions change setup, never records

Installing or removing an Extension changes the setup only — the panels, pages and tools in the workspace. Your case files, documents and history stay exactly where they are, and the same holds for whole WorkBench bundles. AI agents, where a clinic uses them, stay on your terms too: they reach the workspace only through MCP pairing you approve, and every write waits for your confirmation.

WhoWhat they can do
Clinic ownerIssues FCX-XXXXXX codes, revokes lost or retired devices on the admin Devices page, raises a device limit, resets the licence password.
Clinic userDoes the daily work on a trusted device, and installs or removes Extensions from the marketplace — setup only, records untouched.
FocusCaseX supportAnswers licence mail — a lost code is reissued against the same licence email in a minute.

One licence is one clinic. Codes are bound to a single email, and the devices under it share one workspace — a second clinic needs its own licence, its own email and its own codes.

The full plain-language page, Licences, devices & codes, covers activation, the hardware identity list and device moves field by field. For quick answers, the troubleshooting section of this guide collects the questions that come up most.

Troubleshooting

The things clinics see most often, each with a short answer in plain words. Find what appears on your screen in the left column and read across.

fcx: command not foundThe installer wires the fcx command into your PATH as part of setup, but a terminal that was already open before the install will not see it. Open a fresh terminal and run fcx again — it should answer straight away.
