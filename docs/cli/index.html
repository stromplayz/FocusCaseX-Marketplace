The FCX CLI

The interactive console, the Extensions storefront, the licence flow, the LAN registry host and the local workspace web — every fcx command, in one place.

The CLI installs from this site's own registry — one curl command, binary fcx — and is maintained in the FCX-NPM repo. The install guide keeps the short version; this page is the deep dive.

The FocusCaseX marketplace and its WorkBenches are installable anywhere Node 18 runs. The fcx command line browses the same catalog the Android app browses — same items, same FCX-XXXXXX install codes — from an interactive console (bare fcx on a terminal), a terminal storefront (fcx marketplace) or plain commands. It can host the registry on the clinic LAN (fcx serve), open the whole workspace as a web page served by the machine itself (fcx open), install one-file packs straight from a file, and keep the licence current and the build fresh (fcx alive, fcx update). Both ends update from the same pipeline, so the CLI and the app never drift apart. Every command is in the full guide's command reference too.

Install

Install the CLI

Install once

One command in a terminal — works on Linux, macOS or Windows (WSL/Git Bash):

curl -fsSL https://stromplayz.github.io/FocusCaseX/install.sh | bash

The registry installer checks Node 18+, installs the fcx command and wires your PATH — open a fresh terminal afterwards so the PATH change takes effect. Source and releases: github.com/stromplayz/FCX-NPM.

fcx --version
focuscasex 3.1.0
# the CLI tracks the platform release — same pipeline as the app

The short version, next to the Android install: /install/ · the full guide's walkthrough: install the FCX CLI.

First steps

The setup wizard — fcx setup

Four guided steps

Run fcx setup once per machine and the wizard walks through four steps, ending with a summary checklist and marking setup done in the CLI's settings:

  1. Workspace folder — where installed items live; writability is checked before anything is written.
  2. Catalog — syncs the marketplace catalog into the local cache that fcx sync refreshes.
  3. Account — sign in with the clinic licence (skippable with --skip-login).
  4. First WorkBench — pick and install a workbench bundle (skippable with --skip-workbench).

Options: --dir D picks the workspace folder up front, --yes runs headless with no prompts, --skip-login and --skip-workbench skip their steps. Per-command help: fcx help setup.

When the command's input is piped — or FCX_NON_INTERACTIVE=1 is set — it prints the manual equivalent steps instead of driving a wizard, so scripts never hang:

fcx setup
FocusCaseX setup — non-interactive mode. Run these steps when ready: 1. Choose a workspace folder: fcx config set workspaceDir <path> 2. fcx sync 3. fcx login 4. fcx workbench install <id-or-code> The guided wizard runs in a terminal: fcx setup
# piped input — the manual equivalent, never hangs

Licence

Sign in — one code per device

fcx login

Install does not carry the licence. Your FocusCaseX owner issues one FCX-XXXXXX code per device. In a terminal:

fcx login
  1. Answer the three prompts — your licence email, password (masked) and the FCX-XXXXXX code issued on the admin Devices page (alias: fcx activate).
  2. The machine becomes a trusted device under the licence and counts against the code's device limit.
  3. Trusted devices never re-enter a code — fcx login on a signed-in machine re-verifies the stored licence instead of asking again. Run fcx status to confirm, fcx device for the full identity card the owner sees, or fcx whoami for one line of identity.
fcx status
Not activated — run fcx login.
# fcx login fixes this line; fcx whoami says the same in one line

fcx logout removes the licence from the machine — it stops the keepalive daemon first, and it does not delete the device on the admin Devices page; the owner removes devices there.

Codes, device limits and keepalive. Codes are issued by your FocusCaseX owner for your licence email; a machine counts against the code's device limit — a licence moves by revoking the old machine and activating the new one. The device licence lives on the device itself, private to it — never printed, never synced. Full details: how codes, devices and revocation work, or the security and privacy section of the full guide.

Marketplace

The storefront in the terminal

fcx marketplace

fcx marketplace opens the Extensions storefront: browse by category — Featured, Clinical, Productivity and more — press / to search, enter an item page for the description, rating and install code, and install straight from the list. Esc steps back one level, q quits. Alias: fcx market. Bare fcx install opens the same storefront.

Prefer plain output? fcx catalog prints the whole thing as a table — every item with its install code, kind and name — optionally filtered by kind (fcx catalog capsule) or dumped as JSON with --json for scripts:

Installing

fcx install and fcx uninstall

One command for every kind

fcx install installs Extensions, capsules, themes, templates and snippets, and WorkBench bundles. Point it at an exact item id, an FCX-XXXXXX install code, or a case-insensitive piece of the item's name — ambiguous matches are listed instead of guessed. Bare fcx install opens the storefront; fcx install list prints what is installed; --dir D overrides the destination folder and --json makes install list scriptable.

fcx install FCX-NX338Z
OK manifest.json OK main.js ╭─────────────────────────────────────────────────────────────────╮ │ Installed Heading Numbering v1.0.0 │ │ Code FCX-NX338Z │ │ Where the item's own folder in the CLI workspace │ ╰─────────────────────────────────────────────────────────────────╯ Enable it in the app: Settings → Extensions → install by code FCX-NX338Z

Every install lands as one folder per installed item in the CLI's workspace — Extensions, capsules, themes, templates and snippets each get a folder for their kind, and WorkBenches go through the workbench installer. The install is registered on the machine, so fcx install list shows it alongside everything else:

fcx install list
╭────────────────────────────────────────────────────────────────────────────────────────────────────╮ │ Name Kind Version Code Folder │ │ Heading Numbering extension 1.0.0 FCX-NX338Z the CLI workspace │ │ Midnight Plus theme 1.0.0 FCX-XKPJSD the CLI workspace │ ╰────────────────────────────────────────────────────────────────────────────────────────────────────╯ 2 items installed fcx uninstall <id-or-code> removes one.
# a fresh machine prints: Nothing installed yet — fcx marketplace to browse.

fcx uninstall <id-or-code> removes an item again — it deletes the item's own folder and updates the installed list. It resolves the same way install does and asks for confirmation on a terminal; piped input removes without prompting.

To switch an item on in the app, install it there by the same code: Settings → Extensions (or Settings → Marketplace for the other kinds) → install by code. Browsing, ratings and how the catalog works: the marketplace section of the full guide.

WorkBenches

WorkBench bundles

fcx workbench list | show | install

A WorkBench is a bundle: one install lands a complete clinical setup. fcx workbench list prints the bundles with their install codes, fcx workbench show <id-or-code> fetches the bundle and prints the full contents — every piece that will land — and fcx workbench install <id-or-code> installs it, with --dir D to pick the destination. The argument resolves the same way fcx install does: an exact item id (workbench:solo-optometry), an FCX-XXXXXX code, or a name substring.

fcx workbench list
CODE ID NAME FCX-2VJD2S workbench:solo-optometry Solo Optometrist WorkBench One install. A complete solo optometry EMR. 1 workbench · fcx workbench show <id-or-code> for details

The install writes the workspace mirror for the bundle — it does not touch any app data. What the Solo Optometrist WorkBench carries, piece by piece: the WorkBench section of the full guide.

Packs

One-file packs, straight from the file

Every installable item is a folder of small files — zip the folder and rename the zip to the item's pack extension, and the file itself becomes the installer: .fcxext for an Extension, .fcxtheme for a theme, .fcxcapsule for a capsule, .fcxwb for a WorkBench, .fcxtemplate for a template, .fcxsnippet for a snippet. Hand the file to fcx install and it reads the pack straight off the file itself — no marketplace round trip, no network — so packs travel by email, USB stick or a shared clinic folder. The pack must carry its manifest at the top of the archive (the bundle's workbench.json for WorkBench packs); the files land as one folder per installed item in the CLI's workspace, the install joins fcx install list like any other, and the printed code switches the item on in the app. The full format specification, every manifest field included: one-file packs.

fcx install ~/Downloads/midnight-plus.fcxtheme

On phones and tablets a received pack loads straight from the file too. How to zip, what the installer checks first, and the six extensions in detail: the pack section of the full guide.

Hosting

Host the registry on your clinic network

fcx serve turns the machine it runs on into the registry for the whole clinic. It hosts a marketplace mirror from the local cache — the catalog copy fcx sync maintains — over HTTP: port 4319 by default, --port to change it. It prints two URLs when it starts: one for the machine itself and one LAN address per network card. When a clinic network exists, point a browser at the LAN URL from any computer on it and the same catalog is right there — other machines can browse and install straight from this machine's cache. No clinic network? Nothing breaks — the server simply answers on localhost only, and the hosted web workspace remains the way in from anywhere.

The mirror serves what the cache holds, so run fcx sync first on a machine that has never synced — the shared copy refreshes every time the cache does. Ctrl+C stops the server.

Endpoint What it serves
/healthStatus and version — a quick check that the server is up, with item and workbench counts.
/api/catalogThe full catalog, in the same shape the app installs from.
/api/workbenchesEvery WorkBench with its install code.
/api/workbenches/<id>One WorkBench bundle, ready to install — by id, code or name.
/A small HTML index of the mirror.

How the mirror fits into an offline clinic, and how it differs from fcx open below: the local workspace web section of the full guide.

The workspace, served by your machine

fcx open — the local workspace web

fcx open runs the FocusCaseX workspace web app on this machine and opens it in the browser — and everything the page shows is served by the machine itself: the licence status, the installed items, the synced catalog and the WorkBench bundles. No internet is needed at all; the only network touch is fetching a WorkBench bundle the machine has not cached yet, the same rule fcx install follows. When the machine sits on a clinic network the server also answers on its LAN address — fcx open prints it right under the Local line — so the front desk or the testing room can open the very same page from another device on the same Wi-Fi. With no network at all nothing breaks: the page still comes up on localhost, the catalog table reads from the local cache, and only a never-cached bundle would wait. And when the workspace should follow you anywhere — a second site, a laptop on the road — the hosted web workspace at focuscasex.vercel.app remains the way in.

Three ways to run it

  1. fcx open — the workspace page on the default port, 4320; the browser opens by itself.
  2. fcx open --port N — pick the port yourself, for example fcx open --port 8080. If 4320 is already taken without an explicit port, the command moves to the next free one on its own; a --port you named that is busy stays an error, with the next port suggested.
  3. fcx open --no-open — start the server without opening a browser, for a machine you plan to reach from another device on the clinic network.

Ctrl+C stops the server. Started from the console menu (bare fcx), stopping hands control back to the menu instead of ending the session. A few small check-up addresses sit under the page — /health and /api/status return the account email, a device summary and counts in plain JSON, and nothing more personal than that.

The fuller story — sharing across the clinic network, the port fallback, the myth about Wi-Fi: the local workspace web section of the full guide.

"The local web only works on a Wi-Fi" is a myth. It works with no network at all — the page is served by the machine itself, and the internet is only ever asked for a bundle that is not cached yet or a catalog sync. The LAN address appears only when a clinic network exists; its absence is normal, not a fault. If a page will not open, troubleshooting has the fix.

Care

The keepalive daemon — fcx alive

The keepalive daemon re-checks this machine's licence with the registry on a schedule — any interval from 5 to 1440 minutes, 10 by default — so the admin Devices page always shows the machine as current, without anyone remembering to. Four forms: fcx alive start runs it in the background, detached from the terminal (a licence is required); fcx alive run keeps the same loop in the foreground until Ctrl+C stops it; fcx alive status — the default — shows whether it is running, since when, and the recent pings; fcx alive stop stops it. Signing out (fcx logout) stops it automatically. The interval is a CLI setting: fcx alive start --interval N stores a new value, or change it with fcx config set keepalive.intervalMinutes.

The licence itself stays private on the machine; security and privacy explains what the checks send and what they never share, and the account section of the full guide covers the sign-in flow the daemon keeps current.

Updates

Staying updated — fcx update

fcx update compares the build on this machine against the registry's catalog — the CLI block with its version and install command. When a newer CLI has shipped, it prints the registry's one-line installer to copy and run; when this build is the current release, it says so:

fcx update
FocusCaseX CLI update installed focuscasex 3.1.0 registry focuscasex 3.1.0 OK You're up to date — focuscasex 3.1.0 is the registry's current release.

Or simply re-run the install command from the top of this page; fcx --version confirms the build afterwards. Network trouble here is a warning, not a failure — the command exits cleanly and you can retry later. The app and the CLI ship from the same pipeline, so a release lands on both ends together. The care routine around updates: keeping the clinic current.

Settings

CLI settings — fcx config

The CLI's settings are dotted keys, and fcx config reads and writes them: fcx config list prints every key with its value, fcx config get <key> and fcx config set <key> <value> read or change one, and fcx config reset returns everything to the defaults (it asks first on a terminal). The keys: workspaceDir — the installed-items folder, empty for the default; setupDone — the setup wizard has finished; keepalive.intervalMinutes — the keepalive ping interval, 5 to 1440 minutes; appearance.accent — the accent color. set reads true/false as booleans and plain numbers as numbers; unknown keys are rejected with the key list as a hint.

Catalog

Refresh the catalog — fcx sync

fcx sync fetches a fresh copy of the marketplace catalog into the local cache that it maintains, then prints what it received — items, workbenches, snippets. Run it after setup, whenever the marketplace adds something new, or whenever the catalog list looks stale; the cached copy is also what keeps installs, fcx catalog, fcx serve and fcx open working while the network is down. Self-hosting a mirror? FCX_MARKET_URL points the sync (and the rest of the CLI) at your own registry.

fcx sync
Syncing marketplace catalog saved to the local cache items 92 workbenches 1 snippets 7

The cache is also the first thing fcx vitals checks. Refreshing as part of the care routine: keeping the clinic current.

Diagnostics

Vitals and stats

fcx vitals — the health check

fcx vitals runs eight checks and prints one OK/WARN/FAIL line for each: Node 18 or newer, the CLI's data home accepting writes, the settings reading back cleanly, the device licence — verified with the registry when online — the catalog cache, marketplace reachability, the keepalive daemon, and the items installed here. It exits with code 0 unless a check fails outright; network problems come back as warnings, not crashes, and the CLI keeps working from the cached catalog. --offline skips the network checks — handy on a machine that is never online. fcx doctor is the same command under a friendlier name.

fcx vitals --offline
▐ FocusCaseX Console · v3.1.0 focuscasex v3.1.0 OK Node 24.22.3 (>= 18 required) OK FCX home writable — … OK Config readable (defaults — no settings saved yet) WARN Not signed in (fcx login) WARN No cached catalog (run fcx sync) WARN offline — cached catalog will be used (--offline set) WARN Keepalive off — fcx alive start (optional) WARN Nothing installed yet (fcx marketplace) 8 checks · 3 ok · 5 warn · 0 fail
# a fresh machine before setup — the WARN lines are simply things not done yet

fcx stats — what this machine has been doing

fcx stats is the local usage dashboard: an overview of counts (commands run, installs, sign-ins, syncs, keepalive actions, update checks, licence and keepalive state), the commands run most often, and the most recent activity, each in its own box. Everything it shows is built on the machine and stays on the machine — nothing is sent anywhere. --json dumps the summary and recent events for scripts.

Automation

MCP and AI agents — fcx mcp

fcx mcp prints the FocusCaseX MCP server URL, the pairing flow and setup snippets for eight agents — Claude Code, Claude Desktop, Cursor, Windsurf, VS Code, Cline, Gemini CLI and Codex CLI — ready to paste into each one's settings. Pairing works from the app: Settings → MCP → Connect agent, and the app issues a 6-digit code (with a QR holding the same payload); the agent trades that code for the scopes you approved, and every write lands in the app as a pending action you approve or deny.

When something's off

Troubleshooting

Start with fcx vitals — its eight lines usually point straight at the fix (the demo above). The things that come up most, each with a short answer:

What you see What to do
fcx: command not foundThe installer wires your PATH, but a terminal opened before the install will not see it. Open a fresh terminal and run fcx again.
catalog fetch failsRun fcx sync to refresh the cache, or check the network. fcx vitals --offline passes with a cached catalog, so installs keep working without the network.
This screen needs an interactive terminalThe console and the marketplace are full-screen views — they print this hint when the output is piped. Run them in a real terminal, or use the non-interactive paths: fcx catalog, fcx install <id-or-code>.
port already in useStart the server on another port: fcx serve --port <other> or fcx open --port <other>. An explicitly named port that is busy stays an error; without --port, fcx open slides to the next free one on its own.
a pack file will not installA pack is an ordinary zip renamed to its pack extension — it must carry its manifest at the top of the archive (workbench.json for WorkBench packs). Zipping a parent folder puts the manifest one level down, where the installer cannot read it; re-zip the folder so the manifest sits at the top. The layout: one-file packs.
version mismatchRun fcx update — it prints the one-line command when a newer build ships — or re-run the install command from the top of this page, then check fcx --version.
the FCX- code is refusedCodes are exact — paste rather than retype, and make sure it is the code issued for your licence email. If the refusal says the device limit is full, your clinic owner moves the licence: the old machine is revoked, a fresh code is issued, and this machine activates. How devices and limits work.

The longer list, including the Android side: troubleshooting in the full guide and the Updates.
